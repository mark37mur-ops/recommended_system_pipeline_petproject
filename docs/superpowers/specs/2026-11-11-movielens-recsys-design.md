# MovieLens Recommender Service — дизайн

**Дата:** 2026-11-11
**Статус:** черновик. Секции 1–3 согласованы, секция 4 на согласовании, секции 5–6 ещё не обсуждались.

## 0. Цель и рамки

**Что строим.** Сервис рекомендаций фильмов на MovieLens 1M, доведённый до работающей системы: данные → обучение по расписанию → API → мониторинг, с публичной демо-ссылкой.

**Зачем.** Портфолио для поиска работы (ML engineer / MLOps). Стек и структура должны выглядеть как в индустрии, проект нужно уметь показать и объяснить на собеседовании. Вторая цель — научиться, поэтому каждый шаг сопровождается объяснением.

**Что входит:**
- двухэтапная модель: кандидаты ALS (`implicit`) + ранжирование LightGBM;
- оркестрация в Airflow, трекинг и реестр моделей в MLflow;
- FastAPI + веб-страница, Redis, Postgres, всё в `docker compose`;
- **живой цикл обратной связи:** посетитель оценивает фильмы и сразу получает рекомендации, его оценки попадают в переобучение;
- **мониторинг:** Prometheus + Grafana (сервис) и Evidently (данные);
- **CI/CD:** GitHub Actions, тесты → образы → деплой на VPS;
- публичный деплой на один VPS (~8 ГБ RAM).

**Что не входит (кандидаты в v2):** A/B-тест и теневая модель, объяснимость рекомендаций, постеры фильмов, CatBoost (разве что как эксперимент в MLflow), React-фронтенд, регистрация пользователей.

**Принцип работы:** этапы, каждый из которых заканчивается чем-то рабочим и показываемым. Инструменты вводим по одному, тогда, когда без них становится неудобно.

## 1. Архитектура и компоненты

Все компоненты работают на одном VPS в Docker-контейнерах. Тот же `docker-compose.yml` запускается локально.

| Компонент | Ответственность | Связи |
|---|---|---|
| Postgres | Единственный источник правды. Отдельные БД: `app` (movies, users, ratings), `airflow` (метаданные), `mlflow` (backend store) | все через SQL |
| Airflow | Запускает пайплайны по расписанию, ретраи, история запусков | читает `app`, пишет в MLflow, вызывает API |
| MLflow | Трекинг экспериментов + Model Registry. Текущая боевая модель помечена alias `champion` | Airflow пишет, API читает |
| FastAPI | API рекомендаций и оценок, отдаёт веб-страницу | MLflow (загрузка модели), Postgres, Redis |
| Redis | Кэш рекомендаций и счётчики rate limiting | только FastAPI |
| Prometheus + Grafana | Сбор метрик сервиса с `/metrics` и дашборды | опрашивают API |
| Evidently | Библиотека внутри задачи Airflow, HTML-отчёт о дрифте данных | часть DAG |

**Ключевые решения:**
- Одна СУБД Postgres вместо Postgres + DuckDB: живые оценки и датасет лежат в одном месте.
- Модель передаётся **только через MLflow Registry**. API не знает, как модель обучалась. Откат делается переносом alias.
- Посетитель анонимный: `user_id` хранится в cookie, без регистрации и паролей.

### Потоки данных

**Онлайн (секунды):** оценки → `POST /ratings` → Postgres → `GET /recommendations` → fold-in ALS → ранжирование ~100 кандидатов → топ-10 (+ кэш Redis).

**Офлайн (раз в сутки, DAG):** выгрузка оценок → валидация → отчёт о дрифте → split → ALS → ранжировщик → оценка challenger и champion на одной выборке → регистрация → при успехе alias `champion` → API перезагружает модель.

## 2. ML-часть

### 2.1. Разбиение данных
Делим историю каждого пользователя по времени (per-user temporal split), а не случайно. Случайное разбиение даёт утечку будущего.

```
[ ранние оценки → обучение ALS | следующие 5 → обучение ранжировщика | последние 5 → тест ]
```
Пользователи с менее чем 15 оценками целиком идут в обучение ALS. Общая дата среза не используется, потому что живые оценки (2026) отделены от MovieLens (2000–2003) разрывом в 20+ лет.

### 2.2. Этап 1 — кандидаты: ALS (`implicit`)
- Оценки превращаются в confidence-веса (5 — сильный сигнал, 1–2 — слабый). Точная формула подбирается в экспериментах.
- ~100 кандидатов на пользователя, уже оценённые фильмы фильтруются.
- **Fold-in** для новых посетителей: вектор пользователя пересчитывается по его оценкам при фиксированных векторах фильмов (`recalculate_user=True`), без переобучения.

### 2.3. Этап 2 — ранжирование: LightGBM `LGBMRanker` (`lambdarank`)
Признаки:
- от ALS: скор и ранг кандидата;
- фильм: популярность, средняя оценка, жанры, год;
- пользователь: число оценок, средняя оценка, возраст, пол, профессия (у веб-пользователей это NaN);
- пара: доля оценок пользователя в жанрах фильма.

Кандидаты для обучения ранжировщика строит ALS, обученный только на первой части данных, а метки берутся из второй. Так ранжировщик не учится копировать скор, который уже «знает» ответ.

### 2.4. Холодный старт
| Оценок у пользователя | Рекомендации |
|---|---|
| 0 | Онбординг: ~20 популярных фильмов разных жанров, просьба оценить ≥5 |
| 1–4 | Популярное в жанрах, оценённых высоко |
| ≥5 | Полный пайплайн: fold-in ALS → ранжировщик |

### 2.5. Метрики
- **NDCG@10** — главная метрика, по ней выбирается чемпион;
- **Recall@10**;
- **Coverage** — доля каталога, попадающая в рекомендации.

Обязательные базовые линии: popularity → ALS-only → ALS + ranker. Каждая следующая модель должна обгонять предыдущую. Если ранжировщик не лучше ALS, в сервис идёт ALS-only.

## 3. Сервис

### 3.1. Эндпоинты
| Метод и путь | Назначение |
|---|---|
| `GET /` | Страница (Jinja2 + немного vanilla JS): онбординг, поиск, оценки, рекомендации |
| `GET /movies/onboarding` | 20 фильмов для первых оценок |
| `GET /movies/search?q=` | Поиск фильма по названию |
| `POST /ratings` | Upsert оценки `(movie_id, rating ∈ 1..5)` |
| `GET /recommendations?k=10` | Топ-k для пользователя из cookie |
| `GET /health` | Liveness: процесс жив |
| `GET /ready` | Readiness: модель загружена, БД доступна |
| `GET /metrics` | Метрики Prometheus |
| `POST /admin/reload-model` | Перезагрузка чемпиона, защищена токеном из env |

### 3.2. Модель в API
- При старте API загружает артефакты `champion` из MLflow (item factors ALS, ранжировщик, таблица признаков фильмов) и держит их в памяти.
- Горячая замена: новая модель грузится в фоне, затем ссылка на неё подменяется атомарно. При ошибке остаётся старая модель.
- Признаки считает один модуль `features.py`, общий для обучения и сервиса. Это защита от train/serve skew.

### 3.3. Redis
- Кэш: ключ `recs:{user_id}:{model_version}`, TTL 10 минут. Новая оценка инвалидирует ключ пользователя.
- Rate limiting: не больше 30 оценок в минуту на пользователя и на IP.

### 3.4. Защита данных от мусора
1. Валидация Pydantic (диапазон оценки, существование фильма).
2. Уникальный ключ `(user_id, movie_id)`, повторная оценка обновляет запись.
3. Rate limiting, не больше 300 оценок на пользователя.
4. Колонка `source ∈ {movielens, web}`, флаг DAG для обучения без веб-данных.
5. Проверка «не хуже чемпиона» перед выкаткой.

### 3.5. Деградация
| Сбой | Поведение |
|---|---|
| MLflow недоступен при старте | Fallback на popularity, `/ready` сообщает о деградации |
| Ошибка модели на запросе | Popularity + лог + метрика ошибки |
| Postgres недоступен | Запись оценок → 503; рекомендации из кэша, если есть |
| Redis недоступен | Работа без кэша, rate limiting временно отключён |

Целевая задержка: p95 < 100 мс.

## 4. Пайплайны (Airflow) и MLflow — на согласовании

### 4.1. Принципы
- **DAG-файлы тонкие.** Каждая задача — вызов функции из пакета `recsys`. Логику можно тестировать без Airflow.
- **Данные между задачами передаются файлами**, а не через XCom. Каждая задача пишет Parquet в `/data/runs/{run_id}/`, через XCom идут только пути и id. XCom хранится в БД Airflow и не предназначен для больших данных.
- **Идемпотентность.** Повторный запуск задачи даёт тот же результат: пишем в папку конкретного запуска, в БД делаем upsert. Это позволяет безопасно ретраить (`retries=2`).
- **Окружение.** Свой образ на основе `apache/airflow` с установленным пакетом `recsys` (`implicit`, `lightgbm`). Альтернатива, отдельный training-образ через DockerOperator, требует доступа к Docker socket и для одного VPS избыточна.

### 4.2. DAG
**`bootstrap_data`** (ручной запуск, один раз): скачать MovieLens 1M → проверить контрольную сумму → загрузить в Postgres `app`.

**`retrain_daily`** (`@daily`):
```
extract_ratings → validate_data → drift_report → split
  → train_als → train_ranker → evaluate → decide_promotion
      ├─ promote → set_champion_alias → reload_api
      └─ skip    → log_reason
```
- `validate_data`: нет NULL, оценки 1..5, число оценок не упало больше чем на 5% относительно прошлого запуска, нет дубликатов `(user_id, movie_id)`. При нарушении DAG падает громко, обучения на мусоре не будет.
- `evaluate`: challenger, текущий champion и базовые линии считаются **на одном тестовом сплите текущего запуска**.
- `decide_promotion`: продвигаем, если champion'а нет или `NDCG@10(challenger) ≥ NDCG@10(champion) − 0.005` и coverage упал не больше чем на 10%. Небольшой допуск нужен потому, что при почти одинаковом качестве предпочтительна более свежая модель.

### 4.3. Что пишем в MLflow
- **Experiment:** `movielens-recsys`, один run на запуск DAG.
- **Params:** гиперпараметры ALS (factors, regularization, iterations, alpha) и LightGBM, сиды.
- **Metrics:** NDCG@10, Recall@10, Coverage для popularity / ALS-only / ALS+ranker, а также champion на том же сплите.
- **Tags:** git commit SHA, хеш снапшота данных, `n_users`, `n_ratings`, доля `source=web`.
- **Artifacts:** модель, таблица признаков фильмов, HTML-отчёт Evidently.
- **Model Registry:** модель `movielens-recommender` (MLflow pyfunc, внутри ALS + ranker + признаки), версии, alias `champion`. Используются aliases, а не устаревшие stages.
- Артефакты хранятся на диске сервера MLflow (`--serve-artifacts`). Клиенты загружают их по HTTP, общие тома не нужны.
